## 2. Ключевые архитектурные решения (ADR)

### ADR-001: Стек хранения и чистая сборка (`CGO_ENABLED=0`)
- **Решение**: Использовать `modernc.org/sqlite` (драйвер `sqlite`) с `CGO_ENABLED=0`.
- **Обоснование**: Позволяет собирать переносимый исполняемый файл для Windows 10/11 x64 (`GOOS=windows GOARCH=amd64`) без зависимости от C-компилятора (`gcc`/`mingw-w64`) и системных DLL.
- **Настройки SQLite**: `PRAGMA journal_mode=WAL`, `PRAGMA synchronous=NORMAL`, `PRAGMA foreign_keys=ON`, `PRAGMA busy_timeout=5000`.

### ADR-002: Портативный режим (`--portable`, `--data-dir`) и защита от двойного запуска
- **Решение**:
  1. Приоритет выбора каталога данных:
     - Явный флаг `--data-dir <path>` имеет наивысший приоритет.
     - Флаг `--portable` размещает каталог `data/` строго рядом с исполняемым файлом (`filepath.Dir(os.Executable())`), а не в текущем рабочем каталоге (`os.Getwd()`).
     - По умолчанию (без флагов) используется `%LOCALAPPDATA%\ProxyDesk` на Windows (или `~/.local/share/proxydesk` на Linux/macOS).
  2. Перед инициализацией БД проверяется доступность каталога на запись (создание и удаление пробного файла). Если каталог недоступен — возвращается явная ошибка без скрытого переноса данных во временную папку.
  3. Защита от конфликта двух экземпляров (`internal/lock`): создается lock-файл `data/instance.lock` с записью JSON (`pid`, `api_addr`, `started_at`). Если lock-файл занят живым процессом, второй экземпляр проверяет доступность `api_addr`, сообщает пользователю адрес уже запущенного экземпляра (и при интерактивном запуске без `--no-open-browser` открывает его в браузере), после чего штатно завершается с кодом `0`, не убивая чужие процессы и не отбирая порты.

### ADR-003: Политика секретов и дедупликации
- **Решение**:
  - Учетные данные прокси (`username`, `password`) **не сохраняются на диск в открытом виде** по умолчанию: в таблице `proxies` они не записываются в БД, а хранятся только в оперативной памяти процесса (`internal/model.CredentialStore`) на время сессии.
  - В таблицу `proxy_sources` поле `raw_line` записывается только после санитизации (`RedactRawLine`), где `user:pass@` заменяется на `***:***@`.
  - Ключ дедупликации `dedup_key` вычисляется как `SHA-256` от канонической строки `protocol://username:password@host:port` (с добавлением `host:port` префикса без секретов: `protocol://host:port#sha256(user:pass)`). Это гарантирует, что прокси с разными паролями не смешиваются, но сам пароль невозможно восстановить из `dedup_key` в БД.
  - Токен API (`X-ProxyDesk-Token`) генерируется криптостойким ГПСЧ (`crypto/rand`, 32 байта hex) при старте процесса, инжектируется только в главную страницу UI при запросе с валидным loopback `Host` и вырезается из всех логов и диагностических архивов.

### ADR-004: Единая модель возможностей (`CapabilityState`)
- **Решение**: Каждая возможность прокси (`connect`, `auth`, `remote_dns`, `udp`, `tls_to_proxy`) представляется типом `CapabilityState` с пятью строго различимыми значениями:
  - `unknown` — проверка еще не проводилась;
  - `confirmed` — возможность подтверждена успешным тестом в пределах окна свежести;
  - `unsupported` — протокол или сервер явно отклонил возможность (например, код `501`/`405` на `CONNECT` или отказ `SOCKS5` по типу адреса домена);
  - `transient_error` — проверка завершилась сетевым сбоем/таймаутом, не позволяющим сделать вывод о поддержке функции;
  - `stale` — ранее было `confirmed`, но время с момента `last_healthy_at` превысило порог свежести (`capability_ttl`).
- **Следствие**: При выборе маршрута в пуле или шлюзе `unknown`, `unsupported` и `transient_error` никогда не трактуются как `confirmed`.

### ADR-005: Разделение циклов проверки, рейтинга (`score`) и эвристики уверенности (`confidence`)
- **Решение**:
  - Один цикл проверки прокси (`check_cycle`) может опрашивать несколько контрольных целей (`target_url`). Результаты отдельных целей агрегируются в один цикл: три успешных ответа от трех целей в рамках одной проверки считаются **одним** успешным циклом наблюдения, а не тремя независимыми проверками.
  - Результаты `inconclusive` (например, когда недоступны все контрольные цели или нет сети) и `cancelled` (отмена пользователем) записываются в журнал диагностики, но **не изменяют** `consecutive_failures`, `success_rate` и не штрафуют прокси.
  - Показатель `confidence` (`0.0–1.0`) явно документируется и отображается в UI как **эвристическая оценка полноты наблюдений** (учитывающая число независимых циклов $N_{\text{cycles}}$ и временной охват между первой и последней проверкой), а не статистический доверительный интервал.
  - Смена выходного IP (`exit_ip_changes > 0`) сохраняется как отдельный информационный признак (`rotating_exit_ip = true`), но не снижает оценку надежности автоматически (так как ротирующие резидентские/бэкконнект-прокси штатно меняют выходной IP).

### ADR-006: Бюджеты ресурсов и поведение при переполнении
- **Решение**: Установлены жесткие верхние границы для всех очередей и хранилищ:

| Ресурс | Лимит по умолчанию | Поведение при достижении лимита |
| :--- | :--- | :--- |
| Размер тела ответа источника (`max_source_body_bytes`) | `10 MiB` (`10 485 760` байт) | Чтение через `io.LimitReader(r, limit+1)`; при чтении `limit+1` байта загрузка прерывается с явной ошибкой `ErrResponseTooLarge`. |
| Размер ответа контрольной цели (`max_check_body_bytes`) | `64 KiB` (`65 536` байт) | Чтение до `64 KiB + 1`; превышение бракует проверку цели (`ErrCheckBodyTooLarge`). |
| Воркеры чекера (`max_concurrent_checks`) | `64` (настраивается `1..256`) | Ограниченный пул горутин; задачи сверх очереди (`max_check_queue = 10 000`) отклоняются с HTTP `429 Too Many Requests`. |
| История проверок (`check_history` и `check_cycles`) | По `50` последних записей на прокси и не старше `14` дней | Автоматическая подрезка (`DELETE ... WHERE id NOT IN (...)`) при записи нового цикла. |
| Кэш DNS (`max_dns_cache_entries`) | `4 096` записей на политику (группу) | Вытеснение записей с истекшим TTL, затем LRU-вытеснение внутри изолированного namespace группы. |
| Активные соединения шлюза (`max_gateway_conns`) | `512` одновременных сессий | Новые подключения сверх лимита отклоняются (`503` в HTTP / `0x01 General Failure` в SOCKS5) с записью в метрики. |
| Журнал активных/недавних соединений (`conn_ring_buffer`) | `200` записей в памяти | Кольцевой буфер (перезапись самых старых закрытых сессий); подробное логирование доменов выключено по умолчанию (`log_domains = false`). |
| Подписчики SSE (`max_sse_clients`) | `8` клиентов | Отказ новым SSE-подключениям с HTTP `429`; неблокирующая отправка (`select { case ch <- ev: default: drop_counter++ }`), чтобы медленный клиент не блокировал ядро. |
| Файлы логов (`diagnostics/logger`) | `5 MiB` × `3` файла | Ротация `proxydesk.log` → `proxydesk.log.1` → `.2` при превышении 5 МБ. |
